Why this exists

Agents that run on a schedule have no memory between sessions unless you build it into the repo they operate on. Left alone, that leads to one of two failure modes: the agent forgets what it already decided and thrashes between approaches, or it plows ahead into things — payments, account creation, legal or financial actions — that should have stopped for a human.

This kit is the structure that avoids both, refined over multiple real unattended sessions, including at least one mistake caught mid-plan and corrected before it caused a problem (a platform-terms check that got applied as a gate, not an afterthought — the full story is in the guide). It's a set of plain-text templates and a scheduling pattern, not a framework or a dependency — you can read and modify every line.

What's included

  • Operating manual template — the file your agent reads first, every session. Defines mission, autonomy boundaries, session protocol, and hard rules.
  • State template — current phase and the exact next action, so a session with zero memory of the last one can pick up correctly.
  • Log template — dated, append-only history of what happened and why, so decisions stay auditable after the fact.
  • Human-tasks template — the queue of things that genuinely need a human, with a batching convention so the agent never stalls a session waiting on one item.
  • Ledger template — a plain financial record format for any agent that touches money.
  • Scheduling pattern — run.sh + macOS launchd plist + cron notes, with overlap prevention (lock file) and per-run logging.
  • Session-prompt template — the one-line prompt the scheduler hands the agent each run.
  • Design-rationale guide — why each file is separate, why human tasks get batched instead of filed as found, why every session ends with a commit, and the specific mistake this pattern is built to catch.

How to use it

  1. Copy the templates into a new or existing repo your agent has access to.
  2. Fill in the operating manual with your project's actual mission and hard limits — the template's structure is generic, the content is yours.
  3. Point your scheduler (launchd, cron, or your own) at run.sh, which hands the agent the session prompt on each run.
  4. Read the design-rationale guide once before you start — it explains the reasoning behind the parts that look over-engineered at first glance but exist because of a specific failure mode.

What this is not

Not a hosted service, not a framework you install, not tied to any one agent product. Plain text and shell scripts you own outright. Not financial, legal, or tax advice — if your agent will touch money or accounts, the operating-manual template includes a section for exactly those hard limits, but you set them.
