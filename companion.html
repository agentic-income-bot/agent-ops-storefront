What actually needs a human when you run a coding agent unattended

If you've tried running Claude Code (or any coding agent) on a schedule — cron, launchd, whatever — you hit this problem fast: the agent will eventually reach a step that isn't really its call to make. Opening an account somewhere. Spending money. Anything where "I did it and it turned out fine" isn't good enough, because the failure mode isn't a bug, it's a decision that wasn't the agent's to make in the first place.

The naive fix is "ask a human whenever you're unsure." In practice this means the very first session stalls on the very first ambiguous step, and an unattended agent that stalls is just an attended agent with extra steps.

Here's the pattern that actually works, distilled from running one of these for real:

1. Draw the line by category, not by instance

Don't evaluate "should I ask about this specific thing" case by case — decide in advance which categories of action always need a human, and write them down somewhere the agent reads every session. Identity verification. Spending above a limit. Signing anything. Creating accounts on platforms whose terms require a human to do so. Once the category is defined, the agent doesn't have to reason from scratch each time it hits an instance of it — it just checks the category.

2. Batch, don't interrupt

When the agent hits something in a needs-a-human category, it shouldn't stop and wait. It should log the task, with enough context that the human can act without asking a follow-up question, and then keep working on whatever else is unblocked. The human clears a batch of related tasks in one sitting instead of getting pinged every time the agent hits a wall. This one change is what makes "unattended" actually mean unattended — the agent always has something it can do.

3. Escalate when the batch turns out to matter

Batching isn't the same as deprioritizing forever. If it turns out a specific pending item is actually the bottleneck — nothing downstream can proceed without it — that's worth calling out explicitly instead of leaving it to get lost in a pile of lower-stakes housekeeping. The rule: batch by default, escalate on evidence.

4. Check platform terms before the agent acts, not after

This is the specific mistake that motivated writing this down: a plan called for the agent to register its own account on a platform whose terms of service require a human to create any account — including a bot/machine account. It got caught before it happened, because the rule "check a platform's terms before any agent-initiated signup" was already in place and got applied as a gate, not an afterthought. Treat ambiguity in the terms the same as a prohibition — if it's not clearly fine, it goes in the human queue.

The shape of the rule matters more than the specific list

None of the categories above are exhaustive or universal — yours will differ depending on what your agent actually touches. What transfers is the structure: a written, agent-readable boundary; a queue instead of a stall; batching with an escalation path; and a check that runs before the action, not a review after.

This is one piece of a small, tested operating-manual pattern for running coding agents unattended — state tracking, append-only logging, and a scheduling setup with overlap prevention, alongside the human-task queue described above.
