Why this exists

The moment you point a scheduler at an agent CLI and walk away, you inherit two problems every cron/launchd tutorial skips: what happens if a run is still going when the next one is due to start, and what happens if a run crashes and leaves something in a bad state for the next one. Get either wrong and you get silent corruption or a permanently stuck job — exactly the kind of failure you won't be watching for, because the point of scheduling it was to stop watching.

This is the scheduling half of the Agent Ops Starter Kit, split out for people who already have their own agent-memory/state pattern and just want a battle-tested runner.

What's included

  • run.sh template (macOS/Linux) — atomic mkdir-based lock, PID-liveness check to reclaim a stale lock left by a crashed run, one timestamped log file per invocation.
  • launchd plist template (macOS) — a calendar-interval launchd job pointed at run.sh, with the reasoning for RunAtLoad: false and where stdout/stderr go.
  • Windows PowerShell/Task Scheduler template — a native port of the exact same lock/staleness/logging pattern, no WSL or Git Bash required.
  • Cron & other schedulers notes — Linux cron syntax and gotchas, plus when to prefer the native Windows port over a WSL workaround.
  • Design guide — why a directory as the lock (not a lock file), why PID-liveness instead of a timeout, why per-run log files, and how to pick a scheduler for your platform.

What this is not

Not the full agent-memory/state pattern (mission file, state file, log, human-task queue) — that's the Agent Ops Starter Kit, which already includes this scheduling piece. If you don't have your own answer to "how does an agent with no memory between runs know what to do next," get the full kit instead of this and the state pattern separately.
